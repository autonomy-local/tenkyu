# 既存の Firebase 利用者の載せ替え手順

既存の Firebase Auth の利用者を Tenkyu（Account基盤）に載せ替え、各サービス（Bunko、engawa など）との連携を確立するための移行手順書です。

## 概要と基本方針

ADR 0017（Tenkyu の初手）および [docs/schema.md](schema.md) の決定に基づき、以下の原則で移行を行います。

1. **主キーの自社発行**: 利用者（主体）の主キーとして、Tenkyu 側で新しい主体 ID（`sub`。ULID または UUIDv4）を割り当てます。
2. **外部認証の紐付け**: Firebase の `uid` は、Tenkyu の `identities` テーブルに `provider = 'firebase'`、`provider_subject = <uid>` のレコードとして保持します。メールアドレスなどの認証情報は Firebase 側に残します。
3. **個人情報の局所化**: 各サービス（Bunko、engawa 等）には「`uid` → `sub`」の対応表のみを渡し、**メールアドレスは渡しません**。各サービスは Firebase の `uid` を内部の主体 ID（`sub`）に置き換えて管理します。
4. **手順の分離**:
   - **書き出し**: Firebase Auth から利用者一覧を抽出する（今-17b の対象）。
   - **流し込み**: 主体 ID を発行し、Tenkyu の D1（`identities`）に登録して対応表を出力する（今-17c の対象）。

---

## 1. 書き出し（Firebase の利用者の一覧）

Firebase Auth に登録されている既存の利用者一覧を安全にエクスポートします。

### 手順

1. **実行準備**:
   - 移行対象の Firebase プロジェクトへの読み取り権限（Firebase Admin サービスアカウント鍵、または適切な権限を持つ Firebase CLI / gcloud CLI）を用意します。
2. **利用者一覧の抽出（今-17b スクリプトの実行）**:
   - Firebase Auth のエクスポート機能（または Admin SDK の `listUsers` API）を用いて、利用者のリストを中間 JSON / CSV ファイルに書き出します。
   ```sh
   # 実行例（Firebase CLI または専用スクリプトを使用）
   firebase auth:export users_export.json --format=json --project=<project-id>
   ```
3. **抽出データの確認**:
   - `uid`、`email`、`disabled`（無効フラグ）などが取得できているか確認します。
   - レコード総数（件数）を記録します。
4. **中間ファイルの保護と破棄**:
   - この中間ファイルにはメールアドレス等の個人情報が含まれるため、暗号化された安全な領域（手元のメモリや一時ディレクトリ）でのみ扱い、Git リポジトリや公開ストレージにはコミット・保存しません。
   - 移行完了後は安全に完全消去します。

---

## 2. 流し方（Tenkyu への登録と対応表の生成）

抽出した利用者一覧をもとに、Tenkyu の D1 データベースへレコードを投入し、各サービス向けの対応表を出力します。

### 手順

1. **主体 ID の発行とインポートデータの作成（今-17c スクリプトの実行）**:
   - 中間データから有効な利用者ごとに、一意な主体 ID（`sub`）を生成します。
   - Tenkyu の `identities` テーブル用の SQL（またはインポートデータ）を作成します。
     - `id`: ULID または UUIDv4
     - `sub`: 発行した主体 ID
     - `provider`: `'firebase'`
     - `provider_subject`: Firebase の `uid`
     - `created_at`: 現在の UNIX エポック秒
     - `disabled_at`: Firebase 側で無効化されていた場合は UNIX エポック秒、有効なら `NULL`
2. **Tenkyu の D1 へのデータ投入**:
   - Wrangler CLI を用いて、生成した SQL を Tenkyu の D1 データベースに適用します。
   ```sh
   # 例: D1 へのバッチ投入
   npx wrangler d1 execute tenkyu-db --file=import_identities.sql
   ```
3. **各サービス向け対応表の出力**:
   - 各サービス（Bunko、engawa 等）へ引き渡す「`uid` → 主体の ID」の対応表ファイルを書き出します。

### 各サービスに渡す対応表の仕様

各サービスが自身のデータベース内の Firebase `uid` を Tenkyu の主体 ID（`sub`）へ載せ替えるために使用する対応表のフォーマットです。

- **ファイル形式**: CSV または TSV（ヘッダー行あり）
- **列定義**:
  | 列名 | 型 | 説明 |
  | --- | --- | --- |
  | `firebase_uid` | 文字列 | 移行元の Firebase Auth におけるユーザー ID（`uid`） |
  | `sub` | 文字列 | Tenkyu が発行した新しい主体 ID（`principals.id`） |

> **重要**: 個人情報の局所化（ADR 0017）の原則に従い、**この対応表にはメールアドレスや表示名などの個人情報を絶対に含めません**。各サービスには識別子の対応関係のみを渡します。

## リハーサルと本番で違う点

移行手順の検証（リハーサル）と実際の切り替え（本番）における差異は下表のとおりです。

| 項目 | リハーサル | 本番 |
| --- | --- | --- |
| **対象環境（Firebase）** | Firebase Auth エミュレータ、またはステージング環境 | 本番 Firebase プロジェクト |
| **対象環境（Tenkyu D1）** | 手元のローカル D1（Miniflare）またはプレビュー D1 | 本番 Cloudflare D1 |
| **対象データ** | テスト用ダミーデータ、または本番から個人情報をマスクした検証データ | 実運用の全登録利用者データ |
| **事前バックアップ** | 任意（検証環境の再作成で代替可） | **必須**（移行直前の D1 スナップショット取得および Firebase のバックアップ確認） |
| **サービス運用状態** | サービス稼働中でも実施可能 | 必要に応じて新規登録・変更の停止（メンテナンス窓）を設定 |
| **中間ファイル** | 検証完了後に即時削除 | 移行完了・検収完了まで厳重に暗号化保管し、検収完了後に確実に消去 |
| **各サービスへの反映** | 各サービスの検証環境・テスト DB に対応表を反映して疎通確認 | 本番 DB のデータ移行スクリプトを実行し、本番環境の認証切り替えを実施 |

## 3. 確かめ方（検証手順）

移行が正しく完了したことを多面的に検証します。

### 1. 件数・重複の突き合わせ
- **件数の一致**:
  - Firebase からエクスポートした有効ユーザー件数と、Tenkyu の `identities` テーブルに登録された `provider = 'firebase'` のレコード件数が一致していること。
  - 出力された対応表の行数がエクスポート件数と一致していること。
- **一意性の確認**:
  - `identities` の `(provider, provider_subject)` に重複がないこと（D1 の一意制約エラーが発生していないこと）。
  - 各サービス向け対応表において、`firebase_uid` および `sub` に重複がないこと。

```sql
-- D1 での登録件数確認例
SELECT count(*) FROM identities WHERE provider = 'firebase';

-- 重複確認例（0件であること）
SELECT provider_subject, count(*) FROM identities
WHERE provider = 'firebase'
GROUP BY provider_subject HAVING count(*) > 1;
```

### 2. データベース制約の検証
- `sub` 列や `provider_subject` 列に `NULL` や空文字が混入していないこと。
- 無効化されていたユーザーの `disabled_at` が適切にセットされていること。

### 3. 認証・ログインの疎通確認
- **検証アカウントでのログイン確認**:
  - 事前に指定したテスト用移行済みアカウントで、Firebase Auth の認証トークンを用いて Tenkyu のセッション発行・検証エンドポイントを呼び出し、正常にセッションが作成されること。
  - セッション情報に返される `sub` が、対応表に記載された `sub` と一致していること。
- **無効アカウントのログイン拒否確認**:
  - `disabled_at` が設定されたアカウントでのログインが拒否されること。
- **サービス連携の確認**:
  - Bunko または engawa のテスト環境において、移行後の主体 ID（`sub`）でサービス利用・データ参照が正しく継続できること。

## 4. 戻し方（ロールバック手順）

移行作業中または移行直後に異常（データの欠落、不整合、ログイン障害等）が検知された場合の手順です。

### 1. Tenkyu（D1）側のロールバック

状況の重大度に応じて以下のいずれかを実施します。

- **レコードの論理無効化（影響を最小限に抑える場合）**:
  - 投入したレコードの `disabled_at` を一括更新して無効化します。
  ```sql
  UPDATE identities
  SET disabled_at = unixepoch()
  WHERE provider = 'firebase' AND created_at >= <移行バッチ開始時刻>;
  ```
- **レコードの削除（移行直後かつクリーンに戻す場合）**:
  - 移行バッチで投入した `identities` レコードを削除します。
  ```sql
  DELETE FROM identities
  WHERE provider = 'firebase' AND created_at >= <移行バッチ開始時刻>;
  ```
- **D1 スナップショットからの復元（D1 全体で不整合が発生した場合）**:
  - 作業直前に取得した D1 のバックアップ／スナップショットからデータベースを復元します。

### 2. 各サービス側のロールバック

- 各サービス（Bunko、engawa 等）のデータベース移行（`uid` → `sub` の置換）を適用中または適用後の場合、サービス側で取得していた事前バックアップから復元するか、対応表の逆変換を用いて元の `uid` に戻します。
- サービス側の認証設定を移行前の状態（直接 Firebase Auth を参照する設定など）に切り戻します。

### 3. 中間ファイルと対応表の破棄

- 中断または失敗した移行処理の中間ファイルおよび生成された対応表は、誤適用を防ぐために破棄します。

## 5. Firebase の手段を止める

移行が完了し、新方式（メールの6桁コードまたはパスキー）への定着が確認できた段階で、認証手段としての Firebase Auth への依存を停止します。

> **注意**:
> - ここで扱うのは「認証手段としての停止（Tenkyu での Firebase 受付停止およびクライアント UI からの導線撤去）」です。Firebase のプロジェクトそのものの削除は行いません。
> - ログイン実績等の集計・判定スクリプト（数える口）は次-9b にて整備されます。

### 1. 止める条件

以下の条件のいずれか、または両方を満たしたときに Firebase の手段を停止します。

1. **全員の移行完了**:
   - 既存の全対象利用者が、Tenkyu の新方式（メールの6桁コードまたはパスキー）によるログインを一度以上完了していること。
2. **移行期日の到来と非稼働確認**:
   - あらかじめ関係者（館・運営者等）と合意した移行期限（期日）が到来していること。
   - 直近の一定期間（例: 2週間〜1ヶ月）において、Firebase によるログイン試行・セッション発行実績（`auth_events` における `provider = 'firebase'` の記録）が 0 件であること。
3. **サービス稼働の安定**:
   - 各サービス（Bunko、engawa 等）において、新方式による認証・セッション検証が安定して稼働し、未解決の認証障害がないこと。

また、ADR 0017 の「覆す条件」に記載のとおり、以下の場合にも速やかに停止・切り替えを行います。
- Firebase Auth の料金・規約・提供形態の変更により使い続けられなくなった場合。

### 2. 止める手順

1. **事前通知**:
   - 利用者および関係者に対し、Firebase 認証手段（従来のメール・パスワード等）の提供終了日時と、以後はメール確認コードまたはパスキーでログインする旨を事前告知します。
2. **Tenkyu 側での Firebase 認証受付の無効化**:
   - Tenkyu の環境設定（環境変数または設定フラグ）で Firebase Verifier による検証受け付けを無効化（無効化フラグを有効化）します。
   - または、D1 の `identities` テーブルにおいて、Firebase 連携レコードを論理無効化します。
     ```sql
     -- 停止日時に合わせて Firebase provider のレコードを一括無効化する例
     UPDATE identities
     SET disabled_at = unixepoch()
     WHERE provider = 'firebase' AND disabled_at IS NULL;
     ```
3. **クライアント画面での導線撤去**:
   - ログイン画面（Solid.js 側）から、従来の Firebase 認証フォームやボタン（「従来のメール/パスワードでログイン」等の導線）を非表示化または削除します。
4. **事後監視**:
   - 停止直後の `auth_events` およびアプリケーションログを監視し、予期しない認証失敗や利用者からの問い合わせが発生していないか確認します。

### 3. 戻し方（ロールバック手順）

停止後に新方式でログインできない利用者が多発した場合や、重大な不具合が検知されて緊急で Firebase 認証を再開する必要がある場合の手順です。

1. **Tenkyu 側の設定・レコードの復元**:
   - Tenkyu の環境設定で無効化した Firebase Verifier を再有効化します。
   - `identities` テーブルの `disabled_at` を更新して無効化していた場合、該当レコードを再度有効（`NULL`）に戻します。
     ```sql
     -- 無効化を解除して有効に戻す例
     UPDATE identities
     SET disabled_at = NULL
     WHERE provider = 'firebase' AND disabled_at >= <停止実施時刻>;
     ```
2. **クライアント画面での導線の再表示**:
   - ログイン画面の Firebase 認証フォーム・導線を再表示（デプロイまたは設定切り替え）します。
3. **利用者への周知と原因調査**:
   - 利用者に認証手段を一時的に再開した旨を案内し、新方式でログインできなかった原因（メール到達性の問題、パスキー未対応端末等）を調査して恒久対策を講じます。
