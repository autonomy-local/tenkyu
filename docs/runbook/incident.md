# 障害対応手順書（Incident Runbook）

本稼働においてサービス停止や認証関連の障害が発生した際の、切り分けの順番、確認場所、および連絡手順を定めます。

---

## 1. 症状ごとの切り分け手順

障害発生時、または利用者・連携サービスから異常の報告があった場合は、該当する症状に応じて以下の順番で確認と切り分けを行います。

※ ログの確認や調査にあたっては、入力値（メールアドレス、確認コードなど）をログ等に残さないよう注意してください（ADR 0001, ADR 0004）。

### 症状A: ログインできない（メールコード入力エラー、パスキー認証失敗など）

利用者がログイン画面からログインできない場合の切り分け手順です。

1. **Cloudflare Workers のログを確認する**
   - Cloudflare ダッシュボードの Workers ログ（または `wrangler tail`）を確認します。
   - 認証エンドポイント（`/auth/*` 等）へのリクエストに対して、HTTP 5xx エラーや Worker のクラッシュ（例外ログ）が発生していないか確認します。
   - 外部認証（Firebase Auth 連携等）へのリクエストタイムアウトやエラーレスポンスがないか確認します。
2. **D1 の状態とデータを確認する**
   - Cloudflare D1 のコンソールまたは wrangler で D1 データベースの状態を確認します。
   - `identities` テーブルに該当する識別子が存在するか、レコードが破損していないか確認します。
   - データベースへの接続エラーやクエリの失敗がログに出ていないか確認します。
3. **外部プロバイダ・メール送信サービスの状態を確認する**
   - メールの確認コード方式の場合、後述の「メールが届かない」の手順に沿って Resend の状態を確認します。
   - Firebase 連携アカウントの場合は、Firebase 側の障害情報や認証ログを確認します。

### 症状B: 検証が失敗する（各サービスからの Service Binding 呼び出しエラー）

engawa や Bunko などの連携サービスが Tenkyu にセッションの検証を問い合わせた際、検証に失敗する場合の切り分け手順です。

1. **Cloudflare Workers のログを確認する**
   - Tenkyu（auth Worker）の Workers ログを確認し、Service Binding 経由の検証エンドポイント（`/verify` 等）でエラーや例外が発生していないか確認します。
   - 呼び出し元（各サービス）の Worker ログも確認し、Service Binding のバインディング設定ミス、リクエストタイムアウト、あるいはステータスコード 5xx / 401 のどちらが返っているかを切り分けます。
2. **D1 のセッション・認証記録を確認する**
   - D1 のセッション管理用テーブル（`sessions` や `auth_events`）を確認します。
   - セッションの有効期限切れか、セッションレコードそのものが存在しないか、あるいは D1 への読み取りクエリでエラーが起きていないか確認します。
3. **デプロイ・バージョン間の互換性を確認する**
   - 直近で Tenkyu または各サービスのデプロイが行われていないか確認します（ADR 0003, ADR 0017: 後方互換性と auth を先に出す原則）。
   - API の呼び出し形式やトークン・セッションの検証仕様に食い違いが生じていないか確認します。

### 症状C: メールが届かない（確認コードのメールが届かない）

ログイン時の確認コード（6桁のコード）メールが利用者に届かない場合の切り分け手順です。

1. **Cloudflare Workers のログを確認する**
   - Workers のログを確認し、確認コード生成およびメール送信 API 呼び出し処理で例外やタイムアウトが発生していないか確認します。
   - Resend API の呼び出し結果（HTTP ステータスコードやエラーメッセージ。認証エラー、レートリミット到達など）を確認します。
2. **Resend の管理画面を確認する**
   - Resend のダッシュボード（Emails ログ）を開きます。
   - 送信試行されたメールが「Sent（送信済み）」「Delivered（配信済み）」「Bounced（バウンス）」「Complained（苦情）」「Suppressed」のいずれになっているかを確認します。
   - バウンス等の配信失敗エラーが発生している場合は、送信元ドメイン（DNS、SPF/DKIM/DMARC 設定）の検証ステータスに警告が出ていないか確認します。
3. **D1 の発行記録・レート制限を確認する**
   - D1 の確認コード発行記録や試行回数制御テーブルを確認します。
   - 同一アドレス・IPに対する短時間の連続要求などで発行制限がかかっていないか、有効期限切れとなっていないかを確認します。

## 2. 確認場所（見る場所）一覧

| 確認場所 | 主に見る項目・内容 | 目的 |
| --- | --- | --- |
| **Cloudflare Workers のログ** | ・Workers の実行時エラー・未処理の例外<br>・HTTP ステータス（5xx、4xx）の発生状況<br>・Service Binding や外部 API 呼び出しの所要時間・エラー | Worker 自体の稼働状態、クラッシュの有無、エンドポイントの入出力異常の検知 |
| **Cloudflare D1** | ・セッションテーブル、`identities`、`auth_events` の状態<br>・D1 クエリの成否やタイムアウト<br>・データの不整合や破損の有無 | 認証データやセッション永続化層の異常検知、障害原因の特定 |
| **Resend の管理画面** | ・メール送信ログ（Sent / Delivered / Bounced / Suppressed）<br>・API リクエスト数とレート制限<br>・ドメイン設定（SPF / DKIM / DMARC）の認証状況 | メールの到達状況の把握、バウンスや送信制限・ドメイン設定異常の検知 |

## 3. 連絡の順番と体制

障害を検知した際は、速やかに以下の役割順に連絡・共有を行います。
※ 個人名ではなく、役割で記載しています。

| 連絡順 | 連絡先（役割） | 主な連絡手段 | 連絡内容・目的 |
| :---: | --- | --- | --- |
| **1** | **一次対応担当（運用担当）** | 運用チャット（緊急通知チャンネル） / 電話 | 障害の発生、検知した症状、影響範囲の初期報告と一次切り分けの着手共有 |
| **2** | **開発担当（Tenkyu / インフラ担当）** | 運用チャット（インシデント用スレッド） | 切り分け結果（Workersログ、D1、Resendの状況）の共有、修正・ロールバック判断の依頼 |
| **3** | **連携サービス担当（各サービス運用・開発担当）** | サービス連携チャット | 認証基盤の障害状況および各サービス側への影響・暫定対応（キャッシュでの検証維持など）の周知 |
| **4** | **サービス責任者（インシデント統括）** | 運用チャット / 緊急連絡網 | 障害の深刻度、利用者への案内要否（告知・メンテナンス表示）、外部アナウンスの判断依頼 |
| **5** | **利用者・カスタマーサポート窓口担当** | サポート共有チャット / メール | 利用者からの問い合わせ対応方針、障害状況と復旧見込みの伝達 |
