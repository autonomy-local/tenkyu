# M1 リリース手順書（配備・載せ替え・戻し方）

最小構成の稼働（11/16）から最初の導入先に渡すまで（11/23）の間に、本番と同じ手順で配備と載せ替えを検証・実施するための手順書です。

---

## 1. 配備の手順

配備の考え方および役割分担の原則は [docs/deploy.md](../deploy.md)（および [ADR 0003](../decisions/0003-リポジトリ・秘密情報・デプロイ.md), [ADR 0017](../decisions/0017-Tenkyu（Account基盤）の初手.md)）に基づきます。

### 役割分担と基本原則
- **Pulumi**: D1 データベース、Cloudflare Access ポリシー、Worker の基本設定、Service Bindings の結び付け、秘密の値の宣言。
- **wrangler**: Worker アプリケーションコードの配備、D1 マイグレーションの適用。
- **配備順序（厳守）**: 複数サービスが連携する構成において、依存関係の上流となる **Tenkyu（auth Worker）を常に先行して配備** し、その後に呼び出し側の各サービス（engawa、Bunko 等）を配備します。

```
[Tenkyu (auth Worker)] (先に配備)
        ▲
        │ Service Binding
[呼ぶ側のサービス] (後から配備: engawa, Bunko など)
```

### 配備の実行手順

1. **インフラ構成の適用（Pulumi）**:
   - Pulumi CLI を用いて D1 データベースや Service Bindings 等の設定を適用・確認します。
   ```sh
   pulumi up
   ```
2. **Tenkyu の D1 マイグレーションの適用（wrangler）**:
   - 最新のスキーマ変更を反映するため、Tenkyu の D1 に対してマイグレーションを実行します。
   ```sh
   wrangler d1 migrations apply tenkyu-db --remote
   ```
3. **Tenkyu（auth Worker）の配備（wrangler）**:
   - Tenkyu のアプリケーションコードを配備します。
   ```sh
   wrangler deploy
   ```
4. **呼び出し側サービス（engawa、Bunko 等）の配備**:
   - Tenkyu の正常稼働およびヘルスチェックを確認後、呼び出し側各サービスのコード配備を実施します。

## 2. 載せ替えの手順

既存の Firebase Auth 利用者を Tenkyu（Account基盤）に載せ替える手順です。詳細な仕様とスクリプト実行手順は [docs/migration.md](../migration.md) を参照してください。

### 基本方針
1. **主キーの発行**: 利用者の主キーとして Tenkyu 側で新しい主体 ID（`sub`）を割り当てます。
2. **外部認証の紐付け**: Firebase の `uid` は、Tenkyu の `identities` テーブルに `provider = 'firebase'`、`provider_subject = <uid>` として登録します。メールアドレス等の認証情報は Firebase 側に残します。
3. **個人情報の局所化**: 各サービス（engawa、Bunko 等）には「`uid` → `sub`」の対応表のみを引き渡し、**メールアドレス等の個人情報は絶対に渡しません**（ADR 0017）。

### 載せ替えの実行手順

1. **Firebase 利用者一覧のエクスポート（書き出し）**:
   - [docs/migration.md](../migration.md)「1. 書き出し」に従い、Firebase Auth から利用者リストを中間ファイルに抽出します。
   - レコード件数を確認・記録します。中間ファイルは安全に取り扱い、作業完了後に完全消去します。
2. **Tenkyu への登録と対応表の生成（流し込み）**:
   - [docs/migration.md](../migration.md)「2. 流し方」に従い、有効な利用者に対して主体 ID（`sub`）を発行し、Tenkyu の `identities` テーブルへ投入する SQL を生成して D1 に反映します。
   ```sh
   wrangler d1 execute tenkyu-db --file=import_identities.sql --remote
   ```
   - 各サービス向けの「`uid` → `sub`」対応表（CSV/TSV）を出力します。
3. **各サービスへの対応表の引き渡しと反映**:
   - 生成された対応表を各サービスに連携し、各サービス側のデータ更新（識別子の載せ替え）を実施します。
4. **載せ替え結果の検証**:
   - [docs/migration.md](../migration.md)「3. 確かめ方」に従い、件数の一致、一意制約の確認、テストアカウントでの疎通確認を行います。

## 3. 戻し方の手順

配備中または載せ替え作業中・直後に問題が発生した場合のロールバック手順です。

### 1. 配備のロールバック
- **Worker コードの切り戻し**:
  - wrangler のデプロイメント履歴を確認し、直前の正常稼働バージョンへロールバックします。
  ```sh
  wrangler rollback
  ```
- **インフラ構成の切り戻し**:
  - Pulumi の変更に問題がある場合は、直前の正常なコミット／スタック状態にロールバックを適用します。

### 2. 載せ替えのロールバック
載せ替え作業に異常が検知された場合は、[docs/migration.md](../migration.md)「4. 戻し方」に沿って速やかに切り戻しを行います。

- **Tenkyu（D1）側のロールバック**:
  - 投入直後かつ影響を最小限にする場合、追加した `identities` レコードを論理無効化します。
    ```sql
    UPDATE identities
    SET disabled_at = unixepoch()
    WHERE provider = 'firebase' AND created_at >= <移行バッチ開始時刻>;
    ```
  - 必要に応じて、投入したレコードの削除（`DELETE FROM identities ...`）または作業直前に取得した D1 のバックアップ／スナップショットからの復元を実施します。
- **各サービス側のロールバック**:
  - 各サービス側で保持している事前バックアップからの復元、または対応表の逆変換を用いて識別子を元の `uid` に戻します。
  - 各サービスの認証設定を移行前の状態に戻します。
- **中間ファイル・対応表の破棄**:
  - 誤適用や不整合の波及を防ぐため、失敗した作業の中間データや生成された対応表は破棄します。

## 4. 確かめる項目

本番リハーサルおよび受託前検証において確認する必須項目の一覧です。

| 項目 | 確認内容 | 日付 | 結果 |
| --- | --- | --- | --- |
| 載せ替えのリハーサル | Firebase 利用者一覧のエクスポートから Tenkyu D1 への投入、対応表生成、検証手順（件数突き合わせ・テスト疎通）が一連の流れで問題なく完了すること | | |
| メールの先読み | メール送信サービス（Resend）経由の確認コードや認証メールにおいて、セキュリティ機構（Microsoft Defender の Safe Links 等）による先読みでコードが無効化・消費されないこと（ADR 0017 実装上の注意 3） | | |
| 組織の PC でのパスキー | 導入先の組織で管理されている PC端末・ブラウザ環境において、パスキーの登録・認証が正常に行えること（ADR 0017 改訂 決めたこと 1、覆す条件） | | |
