# 秘密の値の入れ替え手順（Secret Rotation Runbook）

この手順書は、Tenkyu で扱う鍵や秘密の値が漏えいしたとき（緊急時）、または定期入れ替えのときの作業手順と、入れ替えたあとの検証手順を定めます。

関連 ADR：
- [ADR 0001: セキュリティと扱うデータ](../decisions/0001-セキュリティと扱うデータ.md)
- [ADR 0003: リポジトリ・秘密情報・デプロイ](../decisions/0003-リポジトリ・秘密情報・デプロイ.md)
- [ADR 0017: Tenkyu（Account基盤）の初手](../decisions/0017-Tenkyu（Account基盤）の初手.md)

---

## 共通の原則

1. **秘密情報の平文コミットの禁止**
   - 秘密情報を Git リポジトリに平文でコミットしない（正本は sops + age、または Pulumi のシークレット管理）。
   - コマンドライン履歴やログに秘密情報の値を出力・記録しない。
2. **無停止での入れ替え（Grace Period）**
   - 署名鍵やペアワイズ鍵など、検証や導出に影響する鍵は、新旧両方の鍵を受け付ける移行猶予期間を設けてから旧鍵を無効化する。
3. **漏えい時の対応**
   - 漏えいが疑われる場合は、安全側の判断として即時に新値を発行・適用し、旧値を無効化（Revoke）する。
   - 脆弱性や漏えいの詳細は公開 Issue に書かず、[SECURITY.md](../../SECURITY.md) に従って人に報告する。

## 1. Resend の API キー

### 概要と用途
- 用途：メールの6桁の確認コードを送信する外部サービス（Resend）の認証キー。
- 保存先：Workers のシークレット（例：`RESEND_API_KEY`）および IaC（Pulumi / sops）。
- 影響範囲：ログイン時のメール確認コード送信処理。

### 入れ替えの手順

1. **新しい API キーの発行**
   - Resend の管理画面（API Keys）にログインする。
   - 権限を「Sending access only」（必要最小限の権限）とし、制限ドメインを指定して新しい API キーを発行・コピーする。
2. **正本設定の更新**
   - sops で管理している暗号化秘密情報ファイルを編集する。
     ```sh
     sops secrets/<環境>.enc.yaml
     ```
   - `resend_api_key` の項目を新しいキーの値に更新して保存する。
3. **Cloudflare Workers への反映**
   - Pulumi 経由でデプロイする場合：
     ```sh
     pulumi config set --secret resendApiKey "<新しいAPIキー>"
     pulumi up --stack <環境名>
     ```
   - または wrangler secret で直接設定する場合：
     ```sh
     wrangler secret put RESEND_API_KEY --env <環境名>
     ```
     プロンプトが表示されたら新しい API キーを入力する。
4. **反映の確認**
   - 下記「確かめること」を実施してメール送信が正常に動作することを確認する。
5. **旧 API キーの無効化（Revoke）**
   - 新しいキーでの送信成功を確認後、Resend 管理画面で旧 API キーを削除（Delete / Revoke）する。

### 確かめること

- [ ] **確認コードの送信確認**
  - Tenkyu のログイン画面でテスト用メールアドレスを入力し、6桁の確認コード送信リクエストを行う。
  - 受信トレイに確認コードのメールが届くこと。
- [ ] **コード入力での認証成功確認**
  - 受信したコードを入力し、正常に認証（セッション確立）できること。
- [ ] **Workers 実行ログの確認**
  - Cloudflare Workers のログ（`wrangler tail` またはダッシュボード）を確認し、API 呼び出しエラー（HTTP 401/403）が出ていないこと。
- [ ] **Resend 管理画面の配信ログ確認**
  - Resend の Logs 画面で、新キーによるメール送信イベントがステータス `Delivered`（または `Sent`）として記録されていること。

## 2. ペアワイズの鍵（Pairwise Secret）

### 概要と用途
- 用途：外部の連携先ごとに異なる主体の識別子（ペアワイズ `sub`）を導出するための秘密鍵（ソルト・HMAC 鍵）。
  `sub = HMAC-SHA256(pairwise_key, client_id + ":" + internal_principal_id)`
- 保存先：Workers のシークレット（例：`PAIRWISE_SECRET`）および IaC。
- 影響範囲：外部連携先（将来の OIDC クライアントや地域連携サービス）が受け取る `sub` の値。
  ※ 鍵を変更すると、同じ利用者であっても外部連携先での `sub` が変化するため、原則として計画的に実施する。

### 入れ替えの手順

1. **新しい秘密鍵の生成**
   - 暗号学的に安全な乱数生成器を用いて、十分なエントロピー（32バイト以上推奨）を持つ新しい鍵を生成する。
     ```sh
     openssl rand -hex 32
     ```
2. **移行用設定の準備（二重保持）**
   - 既存の識別子との互換・移行期間を設ける場合は、現在の鍵を旧鍵（`PAIRWISE_SECRET_PREVIOUS`）、生成した新しい鍵を新鍵（`PAIRWISE_SECRET`）として設定できるようにする。
3. **正本設定の更新と反映**
   - sops 暗号化ファイルまたは Pulumi の秘密の値を更新する。
     ```sh
     sops secrets/<環境>.enc.yaml
     ```
   - Cloudflare Workers に反映する：
     ```sh
     pulumi up --stack <環境名>
     # または
     wrangler secret put PAIRWISE_SECRET --env <環境名>
     ```
4. **連携先との整合性確認**
   - 下記「確かめること」を実施し、導出が正常に動作することを確認する。
5. **旧鍵の破棄**
   - 移行猶予期間が終了した後、旧鍵の設定（`PAIRWISE_SECRET_PREVIOUS` など）を削除し、Workers から撤去する。

### 確かめること

- [ ] **ペアワイズ ID 導出処理の正常動作**
  - ペアワイズ `sub` 生成関数（`derivePairwiseSub` 等）のユニットテストまたは検証エンドポイントを実行し、期待されるフォーマット（ハッシュ形式）の `sub` が返ること。
- [ ] **外部クライアント向け ID トークン/レスポンスの検証**
  - 外部クライアント向けの認証フローを実行し、`sub` が正しく発行され、連携先が受け付けられること。
- [ ] **エラーログの不在確認**
  - Cloudflare Workers のログで、ペアワイズ鍵の読み込み失敗や HMAC 計算失敗のエラーが発生していないこと。

## 3. 署名の鍵（KeyStore 署名鍵）

### 概要と用途
- 用途：Tenkyu が発行するトークン、署名付きアサーション、将来の VC などの署名に使用する非対称鍵ペア（Ed25519 または ECDSA P-256）。
- 保存先：秘密鍵は Workers のシークレット / KeyStore。公開鍵は JWKS エンドポイント（`/.well-known/jwks.json`）等で公開。
- 影響範囲：Tenkyu が発行したトークンの各サービス（engawa、Bunko、外部サービス）での署名検証。

### 入れ替えの手順

1. **新しい鍵ペアの生成と kid（Key ID）の採番**
   - 新しい鍵ペアを生成し、一意な `kid`（例：生成日付やハッシュ値 `key-20261101`）を割り振る。
2. **公開鍵セット（JWKS）への新公開鍵の追加**
   - 署名切り替え前に、まず新しい公開鍵を公開鍵一覧（JWKS）に追加する。
   - 各サービスが新旧両方の公開鍵で検証できるようにする（先行配信）。
3. **新秘密鍵の設定と Workers への配備**
   - Workers の秘密の値に新しい秘密鍵を追加する。
     ```sh
     wrangler secret put SIGNING_KEY_CURRENT --env <環境名>
     ```
4. **署名処理の切り替え**
   - Tenkyu のトークン発行処理において、新しく発行するトークンの署名鍵を新しい秘密鍵（新 `kid`）へ切り替える。
5. **猶予期間（Grace Period）の確保**
   - 既存のトークンの最大有効期限（TTL、例：セッションやトークンの有効期間）が経過するまで、旧公開鍵を JWKS に残す。
6. **旧秘密鍵・旧公開鍵の破棄**
   - 有効期限経過後、JWKS から旧公開鍵を削除し、Workers から旧秘密鍵を削除・失効させる。

### 確かめること

- [ ] **新公開鍵の公開確認（JWKS）**
  - `/.well-known/jwks.json` を取得し、新 `kid` を持つ公開鍵が含まれていることを確認する。
- [ ] **新鍵によるトークン発行確認**
  - 新規に認証を行ってトークンを発行させ、ヘッダーの `kid` が新鍵の ID になっていることを確認する。
- [ ] **各サービスでの署名検証成功確認**
  - engawa や Bunko などの呼び出し元サービスが、Service Binding または公開鍵で新しいトークンを正常に検証できること。
- [ ] **旧トークンの猶予確認**
  - 移行猶予期間中、切り替え直前に発行された旧トークンが拒否されずに検証成功すること。
- [ ] **旧鍵破棄後の検証確認**
  - 旧鍵撤去後、古い `kid` を持つ無効トークンが正しく検証失敗（エラー）となること。
