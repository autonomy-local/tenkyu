# Service Binding インターフェース仕様（約束）

Tenkyu（Account基盤）と各サービス（engawa、Bunko 等）が Cloudflare Workers の Service Binding 経由でやり取りするための口の形と返り値の仕様です。

実装に先立ち、サービス側と Tenkyu 側の開発を並行して進められるよう、通信の約束を定義します。

---

## 1. 要求と返り値

各サービスは、Service Binding を通じて以下の3つの口を呼び出します。

1. セッションの検証
2. ログアウト
3. `/auth/*` の転送の扱い

### 1.1. セッションの検証

クライアントから送られたセッショントークンが有効であるかを Tenkyu に問い合わせます。

#### 要求（Request）

| 項目名 | 型 | 必須 | 説明 |
| --- | --- | --- | --- |
| `token` | `string` | 必須 | クライアントから提示されたセッショントークン（平文） |
| `service` | `string` | 必須 | 問い合わせ元のサービス識別子（例: `'engawa'`, `'bunko'`） |

#### 返り値（Response）

検証に成功した場合（有効なセッション）、以下の項目を返します。
**連絡先情報（メールアドレス等）は返り値に含めません。**

| 項目名 | 型 | 説明 |
| --- | --- | --- |
| `valid` | `boolean` | セッションが有効であるか（成功時は `true`） |
| `sub` | `string` | 主体の ID（Mizucho の `principals.id`、OIDC の `sub` クレーム） |
| `service` | `string` | セッションが紐づくサービス識別子 |
| `amr` | `string` | 認証の手段（例: `'email_code'`, `'passkey'`, `'firebase'`） |
| `auth_time` | `number` | 本人確認（認証）が成功した時刻（UNIX エポック秒） |
| `expires_at` | `number` | セッションの絶対有効期限（UNIX エポック秒） |
| `version` | `number` | 応答フォーマットの版（現在は `1`） |

※ 検証に失敗した場合は、`valid: false` と後述の「失敗の種類」を含むエラー情報が返されます。

---

### 1.2. ログアウト

明示的なログアウト時に、サーバー側のセッションを失効させます。

#### 要求（Request）

| 項目名 | 型 | 必須 | 説明 |
| --- | --- | --- | --- |
| `token` | `string` | 必須 | 失効させるセッショントークン（平文） |
| `service` | `string` | 必須 | ログアウトを要求するサービス識別子 |

#### 返り値（Response）

| 項目名 | 型 | 説明 |
| --- | --- | --- |
| `revoked` | `boolean` | セッションが正常に失効処理されたか（`true`） |
| `version` | `number` | 応答フォーマットの版（現在は `1`） |

---

### 1.3. `/auth/*` の転送の扱い

各サービスが受け取った認証画面・認証フローへのアクセス（例: ログイン画面の表示、確認コードの送信・照合等）を Tenkyu に委任（プロキシ転送）するための口です。

#### 転送の仕組み

- 各サービス（engawa、Bunko）の Worker は、`/auth/*` への HTTP リクエスト（GET, POST 等）を受け取った場合、リクエストをそのまま Service Binding 経由で Tenkyu に転送（Fetch）します。
- Tenkyu は認証フローの画面（HTML）や処理結果を直接返し、必要に応じて各サービスのドメインに対するクッキー（Set-Cookie ヘッダー）を発行します。

#### 要求（Request）

| 項目名 | 型 | 必須 | 説明 |
| --- | --- | --- | --- |
| `request` | `Request` | 必須 | クライアントからサービス Worker に届いたオリジナルの HTTP リクエスト |
| `service` | `string` | 必須 | 要求元サービス識別子（HTTP ヘッダー `X-Tenkyu-Service` 等で付与） |

#### 返り値（Response）

| 項目名 | 型 | 説明 |
| --- | --- | --- |
| `response` | `Response` | Tenkyu が生成した HTTP レスポンス（HTML、リダイレクト、Set-Cookie、または JSON） |

---

## 2. 失敗の種類

セッションの検証が失敗した場合、その原因を特定できるよう以下の5種類のいずれかを返します。

| 失敗の種類（識別子） | 判定の理由・意味 |
| --- | --- |
| `expired`（期限切れ） | セッションの絶対有効期限（`expires_at`）を過ぎている。 |
| `revoked`（失効） | 明示的なログアウト等によってセッションが無効化（`revoked_at` が設定）されている。 |
| `limit_exceeded`（上限で切られた） | 同一主体における同時セッション数の上限を超えたため、古いセッションが切断された。 |
| `idle_timeout`（無操作で切れた） | 最終操作時刻（`last_active_at`）から規定の無操作時間が経過した。 |
| `unknown`（不明） | トークンが存在しない、フォーマット不正、または内部障害等で判定できない。 |

検証失敗時の応答フォーマット例：

```json
{
  "valid": false,
  "reason": "expired",
  "version": 1
}
```

## 3. 覚えておいてよい時間（キャッシュ・TTL）

### 目的

単一障害点への対策として、Tenkyu の一時的な停止や瞬断時にもログイン済み利用者の操作を止めないため、呼び出し元の各サービス（engawa, Bunko）側でセッション検証の結果を短い時間キャッシュ（保持）することを許容します。

### キャッシュ時間（案）

| 項目 | 秒数（案） | 理由・備考 |
| --- | --- | --- |
| **検証結果を覚えておいてよい時間（TTL）** | **60秒** | 頻繁な Service Binding 呼び出しを削減しつつ、ログアウトや失効の反映遅延を1分以内に抑えるため。 |

※ この秒数は設計上の提案です。最終的な秒数は Pull Request のレビューにおいて決定します。

---

## 4. 後方互換の決まり

サービスと Tenkyu が独立して配備できるよう、口（インターフェース）の変更には以下の後方互換ルールを適用します。

1. **項目の追加は許可する**
   要求や返り値に新しい項目を任意項目（Optional）として追加することは、互換性を損なわないため版（`version`）を上げずに行うことができます。呼び出し側は未知の項目を無視する必要があります。
2. **項目の削除・意味の変更は版（version）を上げる**
   既存の項目を削除する場合、必須化する場合、または既存の型の意味や挙動を変更する場合は破壊的変更とし、返り値の `version` をインクリメント（例: `1` → `2`）します。
3. **配備の順序**
   常に Tenkyu（呼び出される側）を先にデプロイし、新旧両方の版に対応した後に各サービス（呼ぶ側）をデプロイします。
