# ブランチ戦略：トランクベース開発

## きまり

- **`main` が唯一のトランク**。`main` は常にテストが通り、デプロイできる状態に保つ
- 作業は `main` から切った**短命のブランチ**で行い、**PR で `main` に squash マージ**する。`main` へ直接 push しない（ルールセットで禁止）
- **1つの Issue に1つのブランチ、1つの PR。** 数日以内にマージできる大きさにする。長引きそうなら Issue を分ける
- マージしたブランチは自動で消える。マージ済みのブランチに積み足さず、続きは新しいブランチで始める
- `develop` や `release/*` のような**長く残るブランチは作らない**。リリースは `main` のコミットにタグ（`vX.Y.Z`）を付けて行う
- `main` との差が開いたら、早めに `main` を取り込む（rebase または merge。マージは squash なので、どちらでも `main` の履歴は一直線）

## ブランチの名前

| 作る人 | 名前 |
| --- | --- |
| 人 | `<種別>/<Issue番号>-<短い名前>`（例：`feat/12-invite-form`） |
| Claude | `claude/<Issue番号>-<短い名前>` |
| Jules | Jules が自分で付ける（名前は強制しない） |

種別はラベルとコミットメッセージの接頭辞にそろえる：`feat` `fix` `docs` `chore` `refactor` `test`。

## main のルールセット

正本は [`.github/settings/ruleset-main.json`](../.github/settings/ruleset-main.json)。`scripts/bootstrap-repo.sh` で反映する。

| ルール | 中身 |
| --- | --- |
| PR を必須 | 承認の数は 0（一人で回すため）。レビューのスレッドは解決してからマージ |
| マージの方法 | squash だけ |
| 必須のチェック | CI の `check` ジョブ |
| 履歴 | 一直線（required linear history） |
| 禁止 | force push、`main` の削除 |

## 未完成のコードを `main` に入れるとき

基本は、1つの PR で完結する大きさに Issue を分ける。それでも途中の状態をマージする必要があるときは、次のどれかで `main` のデプロイできる状態を保つ。

- まだどこからも呼ばれない形で入れる（ルーティングやエントリーポイントにつながない）
- 設定や環境変数による機能フラグで、既定は無効にしておく
