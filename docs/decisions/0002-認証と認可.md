## 背景

engawa と Bunko が同じアカウントの基盤を使う。最小構成は 2026-11-16、本稼働は 2026-12-13（仮置き）。既存の利用者は Firebase Auth にいる。

## 決めたこと

認証は Tenkyu 自身が受け持ち、認可（所属と役割）は持たない。決定の本文は ADR 0017 の改訂（2026-10-31）で、ここでは要点だけを書く。

| 項目 | 決めたこと |
| --- | --- |
| 手段 | 主はパスキー、逃げ道はメールの6桁のコード。Firebase は移行の間だけ `identities` の1行として残す |
| 主体の ID | サービスをまたぐ一つの ID（Mizucho の `principals.id`）。所属と役割はテナントごと |
| `sub` | 中のサービスには内部の ID、外の相手にはペアワイズの ID |
| セッション | Tenkyu がサーバー側で持つ。クッキーはサービスのドメインごと。Service Bindings で検証する |
| 同時と無操作 | 上限と時間の数字を受け取って守るだけ。役割の意味は持たない |
| 認可 | 各サービスか、台帳を受け持つ基盤が判定する |

**未決**：アカウントを削除したときに各サービスの記録に何が起きるか（ADR 0006 と合わせて決める）。

## 理由

主体と認証の手段を分けると、手段を替えても利用者の記録と権限が切れない。自前のパスキーと6桁のコードで、LINE の中のブラウザや古い端末でも通る。

## 検討した他の案

- マジックリンク：LINE の中のブラウザと、メールの先読みで失敗するので採らない
- 認証のコードをパッケージにして各 Worker に組み込む：OSS と非公開の部分の境目が見えなくなるので採らない（ADR 0017）

## 覆す条件

- 館の組織の PC でパスキーが使えないと分かったとき：館は6桁のコードを主にする（ADR 0017）
- Firebase の料金や規約が変わったとき：`identities` の別の手段に切り替える
