## 背景

Tenkyu は「この人は誰か」を確かめる基盤で、全サービスの利用者の連絡先と認証の記録が集まる。漏れたときの影響が最も大きいので、持つものと守り方を先に決める。

## 決めたこと

メールアドレスとパスキーの公開鍵は Tenkyu の中だけに置き、各サービスには内部の ID だけを渡す（ADR 0017 改訂の4）。

| データ | 重さ | 置き場所 |
| --- | --- | --- |
| メールアドレス | 個人情報 | Tenkyu の D1 |
| パスキーの公開鍵 | 個人情報に準じる | Tenkyu の D1 |
| 外部の ID と内部の ID の対応（`identities`） | 個人情報に準じる | Tenkyu の D1 |
| セッション、認証の記録（`auth_events`） | 照合できれば個人情報 | Tenkyu の D1 |
| 確認コード | 秘密 | 有効期限つきで保存。**保存の形は未決（ハッシュを提案）** |
| Firebase 側のメールアドレス | 個人情報 | 移行の間だけ Firebase（Google）。#32 で外す |

- パスワードは持たない。所属、役割、業務のデータも持たない
- ログに入力の値（メールアドレス、コード）を残さない
- 署名の鍵は KeyStore の口の後ろに置き、今の中身は Workers の秘密の値（ADR 0017）
- Worker は内部専用（`workers_dev = false`、公開のルートなし）。運営者の入口は Cloudflare Access の後ろ
- 窓口は SECURITY.md。見つけたら公開の場に書かず、作業を止めて人に知らせる

**未決**：脅威モデルの文書を置くか、確認コードの試行回数の上限と発行の間隔、D1 の保存時の暗号化で足りるか。

## 理由

連絡先の置き場所を一か所にすると、守る場所と説明する場所が一つで済む。「個人情報 0件」とは言わず、識別子と記録も個人情報になりうると認めておく。

## 検討した他の案

- 各サービスがメールアドレスを持つ：漏えいの面が増えるので採らない
- 認証をすべて Firebase に任せ続ける：連絡先が国外に残り、手段を替えにくいので採らない

## 覆す条件

- 法令やガイドラインの変更で、置き場所や保存の形の見直しが要るとき
- 確認コードやパスキーの方式に脆弱性が見つかったとき
