# 0017. Tenkyu（Account基盤、OIDC）の初手

- 日付: 2026-10-24
- 状態: 採用（2026-10-31 改訂。下の「改訂（2026-10-31）」が今の決定。それより上は 10/24 の初手の記録として残す）

## 名前

Account基盤の名前は **Tenkyu（天球）**（10/24）。9/24 の構成で「鍵・署名・検証可能な資格情報（DID/VC）」の基盤（Apache-2.0）として予約していた名前に当てる。OIDC のトークンの発行は「署名した資格情報を出す」ことなので、Tenkyu の第一段階とする。Firebase の呼び出し → マジックリンク・Passkey → DID/VC の道筋が、Tenkyu の本来の役割にそのままつながる。

## 背景

- Bunko の年内リリース（アカウントと既存機能の移行）と、Funadansu の proxy（認証・認可は proxy に切り出して OIDC）が、同じアカウントの基盤を使う。これを最初のマイルストーンにする（最小構成の稼働は 2026-11-16、本稼働は 2026-12-13 を仮置き。館との合意で Bunko のアカウント機能を11月中に渡すため）。
- 既存の Bunko の利用者は Firebase Auth にいる。

## 決めたこと

- **初手は Firebase Auth を呼び出す形**にする。本人確認（認証）は Firebase Auth に任せる。
- **主キーは弊社が別に発行した ID**（`principals.id`。主体の台帳は Mizucho が持つ。台帳と証明で分ける）。Firebase の uid は `identities` に `provider='firebase'` の1行として持つだけにする。
- **Account基盤が出す OIDC のトークンの `sub` も弊社の ID**にする。Bunko も Funadansu も Firebase の uid を見ない。
- 後でマジックリンク・Passkey・DID/VC に替えるときは、`identities` に行を足して切り替える。

## 理由

- アカウントの移行が「弊社の ID を発行して Firebase の uid と紐付ける」だけで済み、年内リリースに間に合わせやすい。
- 主キーを自社で持つので、認証の手段を替えても利用者の記録と権限が切れない。

## 実装上の注意

1. **トークンの検証は Workers でできる**：Firebase の ID トークンは、Google が公開している鍵で JWT として検証できる（`jose` などで可能）。Admin SDK は要らない。鍵はキャッシュし、`aud`（プロジェクト ID）、`iss`、有効期限を必ず確かめる。
2. **データの置き場所**：メールアドレスなどの認証情報は Firebase（Google）側に残る。プライバシーポリシーに置き場所（国名）を書く。
3. **メールリンクの先読み**：Firebase のメールリンクでのサインインを使う場合も、メールの先読みでリンクが消費される問題が起きうる。リンク先で JavaScript を走らせて消費する形なら多くの先読みは避けられるが、Microsoft Defender の Safe Links 系で問題が出ないかを移行のリハーサルで確かめる。

## 未決

- **役割ごとの同時ログインの制御**：編集アカウントは同時ログインなし、閲覧アカウントは同時ログインあり、自動ログアウト。セッション（Tenkyu）で役割（Mizucho）に応じて制御する


- OIDC のプロバイダ部分を自前（Workers・Hono）にするか、既製（Ory は Go で Workers の外。Workers で動く OpenAuth などは準拠の度合いとライセンスを要確認）にするか
- ID をテナントをまたぐ共通の ID にするか、テナントごとに閉じるか（Funadansu の未決「共通 ID の位置づけ」と同じ問い）
- 認証の記録の置き場所（国内に置くか）

## 覆す条件

- Firebase Auth の料金・規約・提供の変更で使い続けられなくなった場合 → `identities` の別の手段に切り替える（主キーは変わらない）
- DID/VC やマジックリンクに移る準備ができた場合 → 同上

## 改訂（2026-10-31）

- 背景：engawa の実装がおおむね終わり（10/30）、認証を Firebase Auth の Dev（メールとパスワード）につないで動かした。認証の部分を Tenkyu に切り出す前提で、手段・ID・個人情報の置き場所・つなぎ方を決める。あわせて、VC の発行の方式は国（デジタル庁「属性証明の課題整理に関する有識者会議」）が次年度に発行の要件（署名の鍵の種類・管理・公開の方法）を文書にする予定で、12月前後に固まる見込み。国立印刷局と VESS Labs の VC の実証（2025/5〜11）の報告書も、そのころの公開と見る。2026年6月のデジタル重点計画では AI エージェントでの活用が筆頭
- 方針：Bunko（最小構成 11/16、館に渡すのが 11/23）と engawa に要る分は今作り、国が決めるものは待つ。設計を「今作る」「差し込み口だけ今作る」「先送りすべき」「先送りしてよい」に分ける

### 決めたこと

1. **認証の手段**：主はパスキー（Tenkyu で自前で持つ）。逃げ道はメールの6桁のコード（LINE の中のブラウザ、古い端末、端末をなくした時）。既存の Firebase のメールとパスワードは、移行の間だけ `identities` の `provider='firebase'` の行として残す
   - マジックリンクは、6桁のコードに置き換える。LINE の中のブラウザでリンクが別のブラウザに飛んでセッションが切れる問題と、メールの先読みの問題を両方避けられる
   - **パスキーは 12/13 の本稼働までに足す**。11/16 の最小構成は Firebase と6桁のコードで出す（館の組織の PC でパスキーが使えるかを、その間に確かめる）
2. **主体の ID**：サービスをまたぐ一つの ID（Mizucho の `principals.id`）。所属と役割はテナントごと
3. **外に出す `sub`**：弊社の中のサービス（engawa、Bunko）には同じ内部の ID。外の相手（将来の OIDC の連携先）には、相手ごとに違う ID（ペアワイズ）。総務省に、ふるさと住民登録の認証連携でペアワイズの識別子を求めている（10/30 の連携の資料）ので、自分の基盤でも同じにする
4. **個人情報の置き場所**：メールアドレスとパスキーの公開鍵は Tenkyu の中だけに置く。engawa にも Bunko にも渡さない。各サービスが持つのは内部の ID だけ。外部の ID（Firebase の uid など）と内部の ID の対応は `identities` に分けて持つ。言い方は「個人の情報 0件」ではなく、「氏名や連絡先は Tenkyu の一か所だけ、ほかは識別子と最小の記録」（`sub` とそれにひもづく利用の履歴は、照合できれば個人情報になりうるため。参考：every Tech Blog「個人情報を自社のDBに持たない設計は、どこまでできるのか」2026-10-30）
5. **サービスとのつなぎ方（初手）**：Service Bindings で、各サービスが Tenkyu にセッションの検証を問い合わせる。OIDC の正式なプロバイダは、外の相手とつなぐときまで後回し
6. **セッションとクッキー**：Tenkyu がサーバー側でセッションを持つ。クッキーはサービスのドメインごと。サービスをまたいだシングルサインオンは、OIDC を入れるときに一緒にやる
7. **同時ログインと自動ログアウト**：役割は Mizucho から受け、Tenkyu は「この主体のこのサービスでの同時セッションの上限」と「無操作で切れるまでの時間」を守るだけにする（役割の意味は Tenkyu に持たせない）
8. **Bunko の最初の範囲**：館の中で学芸員と事務スタッフが使う個人のアカウントだけ。閲覧用（館の中で共有しうるもの）は今は扱わない（閲覧用の共有は先送り）
9. **VC の発行の原則**：最終の形では、弊社が単独で組織（自治会など）の名義の証明を出さない。持つ側の財布は作らず、標準（OpenID for Verifiable Presentations）で国や OS の財布に渡す。過去の事実（何年に何の役割をした）と、今有効な資格は別々の証明にする。中身は参加の事実と時間までにして、評価は書かない

### engawa の切り出しの確認の結果と、切り出しの形（10/31）

- 調査の結論（engawa のリポジトリの側）：**条件付きで可能。ただし engawa だけを見れば、今すぐ切り出す利点は小さい**。認証はすでに Workers の上で WebCrypto だけで動いていて、D1 の移行も要らない。切り出すなら、内部専用の auth Worker を Service Binding で呼ぶ形を勧める。リスクはデプロイの順番の管理、単一障害点、テストの構成の複雑化
- **決定：内部専用の auth Worker（Tenkyu）として今切り出し、engawa と Bunko が Service Binding で呼ぶ**。切る理由は engawa ではなく、二つ目のサービス（Bunko、11/16 の最小構成）がもう来ていること。比べた案は「認証のコードをパッケージにして両方の Worker に組み込み、共有の D1 につなぐ」と「engawa はそのまま、Bunko だけ新しく作る」
  - 理由：Tenkyu は OSS（Apache-2.0）と決め打ちなので、独立して配備できる単位にしておく方が筋。パッケージとして非公開のサービス（Mizucho の側）に組み込むより、公開する部分と非公開の部分の境目が、配備の単位としてそのまま見える。最終の形に一度で着く
- リスクの手当て
  - **デプロイの順番**：auth の口は後方互換を守り、必ず auth を先に出す。口の約束（呼び出しの形と返り値）は、毎回の PR で確かめる
  - **単一障害点**：auth が止まると全サービスのログインが止まる（共有の台帳を持つこと自体の性質で、パッケージと共有の D1 にしても同じ）。各サービスはセッションの検証の結果を短い時間だけ覚えておき、一時的な停止に耐える。ログイン済みの利用者の操作は止めない
  - **テストの構成**：Miniflare は複数の Worker と Service Binding を一度に立てられるので、CI の環境（wrangler、手元の D1、Firebase の Auth のエミュレータ）に auth Worker を足す

### ツールチェーンと IaC（10/31 追加）

- **開発の環境は Nix で固める**（flake）。Node.js、wrangler、Pulumi の CLI などの版を flake に書き、手元でも CI（リリースの直前の全部の回し）でも同じ環境を `nix develop` で再現する。開発にコンテナは使わない。OSS として公開するので、外の人が同じ環境を一つのコマンドで立てられることも目的
- **IaC は Pulumi**。D1、Worker のルートと Service Bindings の結び付け、秘密の値、運営者の入口（Cloudflare Access）のポリシーを Pulumi で書く。Worker のコードの配備は wrangler。`cloudflare.config.ts` は使わない
- **フロントエンドは Solid.js、バックエンドは Hono**（ログイン、確認コードの入力、パスキーの登録の画面と、各サービスから呼ばれる口）
  - **メールの確認コードの流れは JavaScript なしでも通る**こと（engawa の簡易版と同じ決まり。らくらくスマートフォン、LINE の中のブラウザ、AI エージェント）。画面はサーバー側で HTML を返し、パスキーのように JavaScript が要る所だけを Solid で足す
- **CSS は、なるべく依存のない素の CSS に寄せつつ、型の付いた CSS-in-JS を使う**。候補の第一は vanilla-extract：TypeScript で書いて、ビルドのときに普通の .css ファイルに書き出す（実行時の JavaScript がない）。色や余白の決まり（デザイン・トークン）を型の付いた約束（テーマの契約）として持てるので、engawa の画面設計の指示資料の6色の決まりを、そのまま型として共有できる。Vite のプラグインで Solid と組み合わせられる。比べた候補：Panda CSS（実行時はないが、仕組みが大きく生成物が多い）、StyleX（型と書き出しは良いが、Solid での使い方が少ない）。最終の判断は最初の画面を作るときに確かめる
- 理由：Pulumi のスタックと Nix の flake がリポジトリにあれば、fork した人が同じ構成を自分の Cloudflare のアカウントに立てられる

### 設計の仕分け

| 区分 | 項目 |
| --- | --- |
| **今作る**（11/16〜11/23） | `principals`（Mizucho）と `identities`（Tenkyu）／既存の Firebase の利用者の載せ替え（engawa、Bunko）／メールの6桁のコード／サーバー側のセッション、サービスごとのクッキー、Service Bindings での検証／同時セッションの上限と自動ログアウト／認証の記録（`auth_events`。ログに入力の値〈メールアドレス、コード〉を残さない。削除の手順と期限） |
| **差し込み口だけ今作る** | 認証手段の差し替え（`Verifier`。Firebase・6桁のコード・パスキー〈12/13 まで〉）／ペアワイズの `sub` を作る関数／署名の鍵の口（KeyStore。今の中身は Workers の秘密の値、後で HSM・しきい値の署名・e シールのどれか）／承認の記録（誰が、どの役割で、何を承認したか。Mizucho の監査の記録。VC の発行の手続きの証拠になる）／セッションの中身（主体、サービス、認証の手段、時刻）を、後で ID トークンの項目に移せる名前で持つ |
| **先送りすべき**（国を待つ） | VC の形式（JSON-LD か SD-JWT か）と財布とのやり取り（OID4VCI・OID4VP の版）／発行元の鍵の持ち方、e シールとの組み合わせ、失効の仕組み（Bitstring Status List）＝デジタル庁の発行の要件（12月前後）と VESS の報告書／AI エージェントへの委任＝12月のデジタル庁の中間整理／ふるさと住民登録との OIDC の連携＝総務省の民間の外部システムとの連携の整理 |
| **先送りしてよい** | OIDC のプロバイダを自前にするか既製品（OpenAuth、CTC の VC Knots〈OSS、OID4VCI・OID4VP 対応、2025/12〉など）か／サービスをまたいだシングルサインオン／認証の記録を国内に置くこと（D1 の置き場所の指定はアジア太平洋まで。プライバシーポリシーに書く） |

### VC の発行元の鍵（先送りの中身のメモ）

| 案 | 中身 | 弱い所 |
| --- | --- | --- |
| ① 弊社が発行元 | Tenkyu の鍵で署名し、中身に「自治会Xが確認」と書く | 信頼の起点が弊社になる |
| ② 自治会の鍵を Tenkyu が預かる | 自治会ごとの鍵を弊社の鍵の保管庫に置く | 弊社が単独で署名できる。「鍵を預からない」に反する |
| ③ 役員が自分の端末の鍵で署名 | 鍵は役員の手元だけ | 役員の交代、端末の紛失、高齢の役員の操作 |
| ④ 署名を複数付ける | Data Integrity の proof set／proof chain（JSON-LD）。JWS の JSON 形式（財布の対応が薄い） | 確かめる側が全部の署名を見る方針を持つ必要がある |
| ⑤ しきい値の署名 | 「会長・役員・弊社の3つのうち2つ」で普通の署名を一つ作る（Ed25519 系なら FROST）。確かめる側からは普通の証明 | 鍵を分ける儀式、ライブラリの成熟度。役員の持ち分はパスキーに入れられない（任意のデータへの署名の拡張は提案の段階）ので、アプリかブラウザの中に持たせる |
| ⑥ e シール | 組織が認証局から e シール用の証明書を受け、VC に入れる（JSON-LD でも SD-JWT でも可。サイバートラストと Recept の実証、2024/11） | 審査は登記が前提。任意団体の自治会は受けられず、認可地縁団体（地方自治法260条の2）なら受けられる可能性 → 認可地縁団体になることが、国の信頼の枠組みの中での正式な発行元の入口になりうる |

- 段階：今は VC を出さない（一つの団体の中なら記録と Tenkyu の署名付きの PDF・JSON で足りる）→ 自治会をまたぐ最初の用途（例：本土の自治会での役割の記録を、宮島のコミュニティの入口で信頼の証明として見せる）で、①に役員のパスキーでの承認を必須にして出す（弊社が技術的には単独で署名できる点は隠さず引き受ける）→ 最終の形は⑤か⑥
- 発行の手続き（誰が承認したか）を、第三者が確かめられる記録として残す（有識者会議の﨑村委員の指摘と同じ）

### 覆す条件（追加）

- 館の組織の PC でパスキーが使えないと分かった場合 → 館は6桁のコードを主にし、パスキーは任意にする
- デジタル庁の発行の要件が、上の原則（弊社が単独で組織の名義の証明を出さない）と両立しない形で出た場合 → この節を見直す
